**项目资源（Project Resource）** 是绑定到[项目](/workspaces)上的有类型指针。今天它可以是 Git 仓库 URL，之后也可以是 Notion 页面或文档链接。当[智能体](/agents)处理该项目下的 issue 时，守护进程会把项目资源列表写进智能体工作目录，并写入它的 [meta-skill](/skills) 提示词。

结果是：智能体知道要检出哪个仓库、哪些文档是这个项目的主要参考，而不需要任何人把上下文复制粘贴到 issue 正文里。

## 心智模型

项目不再只是一个标签，而是一个小型**资源容器**：

- 一个项目可以有 0..N 个**资源**。
- 一个资源有 `resource_type`（例如 `github_repo`）和 `resource_ref`（由 `resource_type` 决定结构的 JSON 载荷）。
- 新资源类型只需要增加一个字符串和一个处理器。**不用数据库迁移，也不用重写前端。**

这个结构是有意设计的，和 Multica 已经用于智能体 provider 的模式一致：一个 `type` 判别字段，加上对应的类型化载荷。这样 schema 保持稳定，后续添加 “Notion 页面”、“Google Doc”、“上传文件” 或 “外部 URL” 都只是小而增量的改动。

## 目前支持：`github_repo`

第一个资源类型已经可用：

```json
{
  "resource_type": "github_repo",
  "resource_ref": {
    "url": "https://github.com/owner/repo",
    "default_branch_hint": "main"
  }
}
```

`default_branch_hint` 是可选字段。如果提供，守护进程会在 meta-skill 中提示智能体应该基于哪个分支工作。

## 创建项目时绑定仓库

在 **Web** 或 **Desktop** 应用里打开“新建项目”，现在会在 Status / Priority / Lead 旁边看到 **Repos** 选项。选择工作区已绑定仓库，或粘贴一个临时 URL，都会在项目创建时作为 `github_repo` 资源一起绑定。

用 **CLI**：

```bash
# 创建项目并一次性绑定资源。server 会在同一个事务中创建项目和资源；
# 如果资源无效，整个创建会回滚，避免留下只绑定了一半资源的项目。
multica project create \
  --title "Agent UX 2026" \
  --repo https://github.com/multica-ai/multica

# 后续管理资源
multica project resource list <project-id>
multica project resource add  <project-id> --type github_repo --url <url>
multica project resource remove <project-id> <resource-id>

# 通用入口：只要 server 认识这个 resource_type，就不需要改 CLI：
multica project resource add <project-id> \
  --type notion_page \
  --ref '{"page_id":"…","title":"…"}'
```

`--repo` 可以重复传入；每个值都会作为独立的 `github_repo` 资源绑定。

## 智能体运行时会看到什么

当守护进程为项目内的 issue 启动智能体时，会做两件事。

### 1. `.multica/project/resources.json`

API 响应会以结构化形式透传到智能体工作目录：

```json
{
  "project_id": "…",
  "project_title": "Agent UX 2026",
  "resources": [
    {
      "id": "…",
      "resource_type": "github_repo",
      "resource_ref": {
        "url": "https://github.com/multica-ai/multica",
        "default_branch_hint": "main"
      }
    }
  ]
}
```

Skill、辅助脚本或智能体自身都可以解析这个文件，拿到本次运行所需的**精确**资源集合。

### 2. meta-skill 提示词中的“项目上下文”

智能体的 `CLAUDE.md` / `AGENTS.md`（取决于 provider）会加入一段可读摘要：

```md
## Project Context

This issue belongs to **Agent UX 2026**.

Project resources (also written to `.multica/project/resources.json`):

- **GitHub repo**: https://github.com/multica-ai/multica (default branch: `main`)

Resources are pointers — open them only when relevant to the task. For
`github_repo` resources, use `multica repo checkout <url>` to fetch the code.
```

这段文字刻意保持简短。完整载荷在磁盘上；提示词只负责告诉智能体这个项目存在，以及它绑定了哪些资源。

### 失败模式

资源获取是 **best-effort**。如果 API 调用失败，提示词中会省略项目上下文，也不会写入资源文件，但任务仍会启动。智能体不会因为缺少项目上下文而阻塞。

## 添加新的资源类型

这个抽象的目的就是让新类型足够便宜。完整路径是：

1. **Server 校验器**（`server/internal/handler/project_resource.go`）在 `validateAndNormalizeResourceRef` 中添加一个分支，解析并规范化新载荷。
2. **守护进程 meta-skill 格式化器**（`server/internal/daemon/execenv/runtime_config.go`）在 `formatProjectResource` 中添加一个分支，把新类型渲染成可读 bullet。
3. **TypeScript 类型**（`packages/core/types/project.ts`）扩展 `ProjectResourceType`，并添加对应载荷接口。
4. **UI 渲染器**（`packages/views/projects/components/project-resources-section.tsx`）在 `ResourceRow` 中添加新类型分支。

这里**没有 schema 迁移**，没有新的 sqlc query，没有新 endpoint，**也不需要 CLI 改动**。CLI 的通用 `--ref '<json>'` flag 会接受校验器认识的任何载荷，所以新类型首日支持只需要上面四步。（之后可以选择再加一个按类型定制的 CLI 快捷参数，但不是必需。）

同一张 `project_resource` 表和同三个 CRUD 调用处理所有类型。

## 工作区仓库与项目仓库

智能体看到的仓库列表（`CLAUDE.md` / `AGENTS.md` 中的 `## Repositories` 块）由守护进程 claim handler 按这个优先级选择：

- **项目至少有一个 `github_repo` 资源** -> 只向智能体展示这些仓库。工作区级仓库会被刻意隐藏，避免智能体猜测哪个仓库属于这个 issue。
- **项目没有 `github_repo` 资源（或 issue 不属于任何项目）** -> 回退到原来的工作区仓库列表。

这样能让智能体的工作集合保持紧凑：当项目明确声明自己的仓库时，它就是权威答案。结构化资源列表 `.multica/project/resources.json` 仍然包含完整集合，所以需要检查全部资源的 skill 依然可以做到。

守护进程在 checkout 侧也保持一致：如果任务带有项目范围的 `github_repo` URL，这些 URL 会被合并进工作区 allowlist，并在智能体启动前同步到本地 repo 缓存。因此，即使某个项目仓库 URL 没有绑定到工作区级别，它仍然可以作为 `multica repo checkout` 的合法参数，守护进程不会把它当成“未配置”而拒绝。allowlist 的拆分是内部实现：工作区级 URL 和任务范围 URL 分开跟踪，所以刷新工作区仓库列表不会在运行中意外撤销项目 URL。

## 当前刻意不做的事

- **跨项目共享。** 目前每个资源只属于一个项目。
- **按 skill 限定资源范围。** 智能体本次运行中的所有 skill 都能看到全部资源；按类型过滤是后续工作。
- **缓存 / 同步。** `github_repo` 只是元数据；checkout 仍按需通过 `multica repo checkout` 发生。Notion / Google Docs 这类类型上线时，才会带来文档文本缓存。

这些省略是有意的。第一版的目标，是用最少的组件验证这个抽象。
