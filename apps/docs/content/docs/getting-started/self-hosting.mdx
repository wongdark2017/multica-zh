## 架构概览

Multica 包含三个组件：

| 组件 | 说明 | 技术 |
|-----------|-------------|------------|
| **Backend** | REST API + WebSocket server | Go（单二进制） |
| **Frontend** | Web 应用 | Next.js 16 |
| **Database** | 主数据存储 | PostgreSQL 17 + pgvector |

每个需要在本机运行 AI agents 的用户，还需要安装 **`multica` CLI**，并在自己的机器上运行 **agent daemon**。

## 前置条件

- Docker 和 Docker Compose

## 快速安装

两条命令完成所有设置：

```bash
# 安装 CLI 并部署 self-host server
curl -fsSL https://raw.githubusercontent.com/multica-ai/multica/main/scripts/install.sh | bash -s -- --with-server

# 配置 CLI、认证并启动 daemon
multica setup self-host
```

这会安装 CLI、拉取最新 self-host 资源、从 GHCR 拉取官方 Multica 镜像，并把所有内容配置为 localhost。然后打开 http://localhost:3000 并选择登录方式：推荐在 `.env` 中配置 `RESEND_API_KEY` 使用邮件验证码；或不配置 Resend，从 backend logs 中复制生成的验证码。详情见 [第 2 步：登录](#step-2--log-in)。

<Callout>
如果 self-host server 已经在运行，而你只需要在 macOS/Linux 机器上安装 CLI，请使用 Homebrew：`brew install multica-ai/tap/multica`。
</Callout>

<Callout>
如需分步设置，请继续阅读。
</Callout>

## 分步设置

### Step 1 — 启动服务器

```bash
git clone https://github.com/multica-ai/multica.git
cd multica
make selfhost
```

`make selfhost` 会自动创建 `.env`，生成随机 `JWT_SECRET`，并通过 Docker Compose 启动所有服务。

默认会从 GHCR 拉取最新稳定 release 镜像。若要从当前 checkout 构建 backend/web，请运行 `make selfhost-build`。如果选中的 GHCR tag 尚未发布，`make selfhost` 会提示你回退到 `make selfhost-build`。`make selfhost-build` 使用本地 `multica-backend:dev` / `multica-web:dev` tags，因此不会覆盖已拉取的 `:latest` 镜像。

准备就绪后：

- **Frontend：** http://localhost:3000
- **Backend API：** http://localhost:8080

<Callout>
如果你更想手动运行 Docker Compose：`cp .env.example .env`，编辑 `JWT_SECRET`，然后运行 `docker compose -f docker-compose.selfhost.yml pull && docker compose -f docker-compose.selfhost.yml up -d`。
</Callout>

### Step 2 — 登录

打开 http://localhost:3000。Docker self-host stack 默认 `APP_ENV=production`（在 `docker-compose.selfhost.yml` 中设置），并且默认没有固定验证码。选择以下任一方式登录：

- **推荐（生产）：** 在 `.env` 中配置 `RESEND_API_KEY`，然后重启 backend。真实验证码会发送到你输入的邮箱。见下方 [配置](#configuration)。
- **未配置 email：** 验证码由 server 端生成并打印到 backend 容器日志中（搜索 `[DEV] Verification code for ...:`）。适合单机临时测试。
- **确定性的本地/私有测试：** 在 `.env` 中设置 `APP_ENV=development` 和 `MULTICA_DEV_VERIFICATION_CODE=888888`，然后重启 backend。`APP_ENV=production` 时会忽略这个固定验证码。

修改 `ALLOW_SIGNUP` 和 `GOOGLE_CLIENT_ID` 后，也需要重启 backend / compose stack 才会生效。Web UI 会在运行时从 `/api/config` 读取它们，因此无需重新构建 web。

<Callout>
**警告：** 不要在公网可访问实例上设置 `MULTICA_DEV_VERIFICATION_CODE`，否则任何知道 email 地址的人都能用该固定验证码登录。
</Callout>

### Step 3 — 安装 CLI 并启动 Daemon

daemon 运行在你的本机，不在 Docker 中。它会检测已安装的 AI agent CLIs、向服务器注册它们，并在任务被分配给 agents 时执行任务。

### a) 安装 CLI 和 AI agent

```bash
brew install multica-ai/tap/multica
```

你还需要至少一个 AI agent CLI：

- [Claude Code](https://docs.anthropic.com/en/docs/claude-code)（`claude` 在 PATH 中）
- [Codex](https://github.com/openai/codex)（`codex` 在 PATH 中）
- [Gemini CLI](https://github.com/google-gemini/gemini-cli)（`gemini` 在 PATH 中）
- OpenCode（`opencode` 在 PATH 中）
- OpenClaw（`openclaw` 在 PATH 中）
- Hermes（`hermes` 在 PATH 中）

### b) 一条命令设置

```bash
multica setup self-host
```

这会自动：

1. 配置 CLI 连接 `localhost`
2. 打开浏览器进行认证
3. 发现你的工作区
4. 在后台启动 daemon

带自定义域名的本地部署：

```bash
multica setup self-host --server-url https://api.example.com --app-url https://app.example.com
```

验证 daemon 是否运行：

```bash
multica daemon status
```

<Callout>
也可以逐步配置：`multica config set server_url http://localhost:8080 && multica config set app_url http://localhost:3000 && multica login && multica daemon start`
</Callout>

### Step 4 — 验证并开始使用

1. 在 http://localhost:3000 打开你的工作区
2. 进入 **设置 → Runtimes**，你应该能看到自己的机器
3. 进入 **设置 → Agents**，创建一个新 agent
4. 创建 issue 并分配给你的 agent

## 停止服务

```bash
# 停止 Docker Compose 服务
make selfhost-stop

# 停止本地 daemon
multica daemon stop
```

## 切换到 Multica Cloud

如果你一直在自托管，现在想把 CLI 切换到 [Multica Cloud](https://multica.ai)：

```bash
multica setup
```

这会为 multica.ai 重新配置 CLI、重新认证并重启 daemon。覆盖已有配置前会提示确认。

<Callout>
你的本地 Docker 服务不受影响。如果不再需要，请单独停止它们。
</Callout>

## 升级

```bash
docker compose -f docker-compose.selfhost.yml pull
docker compose -f docker-compose.selfhost.yml up -d
```

如果想停留在某个特定 release，请在 `.env` 中把 `MULTICA_IMAGE_TAG` pin 到精确版本，例如 `v0.2.4`。Migrations 会在 backend 启动时自动运行。如果选中的 GHCR tag 尚未发布，请回退到 `make selfhost-build`，或运行 `docker compose -f docker-compose.selfhost.yml -f docker-compose.selfhost.build.yml up -d --build`。

## 配置

所有配置都通过环境变量完成。复制 `.env.example` 作为起点。

### 必需变量

| 变量 | 说明 | 示例 |
|----------|-------------|---------|
| `DATABASE_URL` | PostgreSQL 连接字符串 | `postgres://multica:multica@localhost:5432/multica?sslmode=disable` |
| `JWT_SECRET` | **必须从默认值修改。** 用于签发 JWT tokens 的密钥。请使用长随机字符串。 | `openssl rand -hex 32` |
| `FRONTEND_ORIGIN` | frontend 服务的 URL（用于 CORS） | `https://app.example.com` |

### Email（认证必需）

Multica 通过 [Resend](https://resend.com) 使用基于 email 的 magic link 认证。

| 变量 | 说明 |
|----------|-------------|
| `RESEND_API_KEY` | 你的 Resend API key |
| `RESEND_FROM_EMAIL` | 发件邮箱地址（默认：`noreply@multica.ai`） |

### Google OAuth（可选）

| 变量 | 说明 |
|----------|-------------|
| `GOOGLE_CLIENT_ID` | Google OAuth client ID |
| `GOOGLE_CLIENT_SECRET` | Google OAuth client secret |
| `GOOGLE_REDIRECT_URI` | OAuth callback URL（例如 `https://app.example.com/auth/callback`） |

修改后需要重启 backend / compose stack 才会生效。Web UI 会在运行时从 `/api/config` 读取 `GOOGLE_CLIENT_ID`，因此无需重新构建 web。

### 注册控制（可选）

| 变量 | 说明 |
|----------|-------------|
| `ALLOW_SIGNUP` | 设为 `false` 可在私有实例上禁用新用户注册 |
| `ALLOWED_EMAIL_DOMAINS` | 可选的逗号分隔 email domain allowlist |
| `ALLOWED_EMAILS` | 可选的逗号分隔精确 email allowlist |

修改后需要重启 backend / compose stack 才会生效。Web UI 会在运行时从 `/api/config` 读取 `ALLOW_SIGNUP`，因此无需重新构建 web。

### 文件存储（可选）

对于文件上传和附件，请配置 S3 与 CloudFront：

| 变量 | 说明 |
|----------|-------------|
| `S3_BUCKET` | S3 bucket 名称 |
| `S3_REGION` | AWS region（默认：`us-west-2`） |
| `CLOUDFRONT_DOMAIN` | CloudFront distribution domain |
| `CLOUDFRONT_KEY_PAIR_ID` | 用于 signed URLs 的 CloudFront key pair ID |
| `CLOUDFRONT_PRIVATE_KEY` | CloudFront private key（PEM 格式） |

### Cookies

| 变量 | 说明 |
|----------|-------------|
| `COOKIE_DOMAIN` | session + CloudFront cookies 可选的 `Domain` attribute。**单 host 部署请留空**（localhost、LAN IP 或单个 hostname）。只有当 frontend 和 backend 位于同一个已注册域名的不同 subdomains 下时才设置它（例如 `.example.com`）。**不要使用 IP literal**，RFC 6265 禁止 cookie `Domain` attribute 中出现 IP 地址，浏览器会丢弃这类 `Set-Cookie` headers。 |

Session cookies 上的 `Secure` flag 会根据 `FRONTEND_ORIGIN` 的 scheme 自动推导：HTTPS origins 得到 `Secure` cookies；plain-HTTP origins（LAN / private-network self-host）得到 non-secure cookies，以便浏览器实际保存它们。

### Server

| 变量 | 默认值 | 说明 |
|----------|---------|-------------|
| `PORT` | `8080` | Backend server port |
| `FRONTEND_PORT` | `3000` | Frontend port |
| `CORS_ALLOWED_ORIGINS` | `FRONTEND_ORIGIN` 的值 | 逗号分隔的 allowed origins 列表 |
| `LOG_LEVEL` | `info` | Log level：`debug`、`info`、`warn`、`error` |

### CLI / Daemon

这些配置位于每位用户自己的机器上，不在服务器上：

| 变量 | 默认值 | 说明 |
|----------|---------|-------------|
| `MULTICA_SERVER_URL` | `ws://localhost:8080/ws` | daemon → server 连接使用的 WebSocket URL |
| `MULTICA_APP_URL` | `http://localhost:3000` | CLI login flow 使用的 frontend URL |
| `MULTICA_DAEMON_POLL_INTERVAL` | `3s` | daemon 轮询 tasks 的频率 |
| `MULTICA_DAEMON_HEARTBEAT_INTERVAL` | `15s` | 心跳频率 |

Agent 专用覆盖项：

| 变量 | 说明 |
|----------|-------------|
| `MULTICA_CLAUDE_PATH` | 自定义 `claude` 二进制路径 |
| `MULTICA_CLAUDE_MODEL` | 覆盖使用的 Claude 模型 |
| `MULTICA_CODEX_PATH` | 自定义 `codex` 二进制路径 |
| `MULTICA_CODEX_MODEL` | 覆盖使用的 Codex 模型 |
| `MULTICA_OPENCODE_PATH` | 自定义 `opencode` 二进制路径 |
| `MULTICA_OPENCODE_MODEL` | 覆盖使用的 OpenCode 模型 |
| `MULTICA_OPENCLAW_PATH` | 自定义 `openclaw` 二进制路径 |
| `MULTICA_OPENCLAW_MODEL` | 覆盖使用的 OpenClaw 模型 |
| `MULTICA_HERMES_PATH` | 自定义 `hermes` 二进制路径 |
| `MULTICA_HERMES_MODEL` | 覆盖使用的 Hermes 模型 |
| `MULTICA_GEMINI_PATH` | 自定义 `gemini` 二进制路径 |
| `MULTICA_GEMINI_MODEL` | 覆盖使用的 Gemini 模型 |

## 数据库设置

Multica 需要 PostgreSQL 17 和 pgvector extension。

### 使用随附的 Docker Compose

```bash
docker compose up -d postgres
```

这会在 5432 端口启动一个 `pgvector/pgvector:pg17` 容器，并使用默认凭据（`multica`/`multica`）。

### 使用你自己的 PostgreSQL

确保 pgvector extension 可用：

```sql
CREATE EXTENSION IF NOT EXISTS vector;
```

### 运行 Migrations

启动 server 前必须运行 migrations：

```bash
# 使用已构建的 binary
./server/bin/migrate up

# 或从源码运行
cd server && go run ./cmd/migrate up
```

## 手动设置（不使用 Docker Compose）

如果你更想手动构建和运行服务：

**前置条件：** Go 1.26+、Node.js 20+、pnpm 10.28+、PostgreSQL 17 + pgvector。

```bash
# 启动你的 PostgreSQL（或使用：docker compose up -d postgres）

# 构建 backend
make build

# 运行数据库 migrations
DATABASE_URL="your-database-url" ./server/bin/migrate up

# 启动 backend server
DATABASE_URL="your-database-url" PORT=8080 JWT_SECRET="your-secret" ./server/bin/server
```

Frontend：

```bash
pnpm install
pnpm build

# 启动 frontend（production mode）
cd apps/web
REMOTE_API_URL=http://localhost:8080 pnpm start
```

## 反向代理

生产环境中，请在 backend 和 frontend 前放置 reverse proxy，用于处理 TLS 和 routing。

### Caddy（推荐）

```
app.example.com {
    reverse_proxy localhost:3000
}

api.example.com {
    reverse_proxy localhost:8080
}
```

### Nginx

```nginx
# Frontend
server {
    listen 443 ssl;
    server_name app.example.com;

    ssl_certificate     /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;

    location / {
        proxy_pass http://localhost:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

# Backend API
server {
    listen 443 ssl;
    server_name api.example.com;

    ssl_certificate     /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;

    location / {
        proxy_pass http://localhost:8080;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    # WebSocket support
    location /ws {
        proxy_pass http://localhost:8080;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_read_timeout 86400;
    }
}
```

当 frontend 和 backend 使用不同 domains 时，请相应设置这些环境变量：

```bash
# Backend
FRONTEND_ORIGIN=https://app.example.com
CORS_ALLOWED_ORIGINS=https://app.example.com

# Frontend
REMOTE_API_URL=https://api.example.com
NEXT_PUBLIC_API_URL=https://api.example.com
NEXT_PUBLIC_WS_URL=wss://api.example.com/ws
```

## 健康检查

backend 暴露公共 health endpoints：

```text
GET /health
→ {"status":"ok"}

GET /readyz
→ {"status":"ok","checks":{"db":"ok","migrations":"ok"}}

GET /healthz
→ same response as /readyz
```

使用 `/health` 做基本 liveness / reachability checks。使用 `/readyz` 做 dependency-aware readiness probes 和外部监控，这样数据库不可用或 migrations 未完全应用时会失败。`/healthz` 作为 operator 习惯用 alias 保留。

## 升级

1. 拉取最新代码或镜像
2. 运行 migrations：`./server/bin/migrate up`
3. 重启 backend 和 frontend

Migrations 是 forward-only，且可安全地在 live database 上运行。它们是幂等的，重复运行不会产生影响。
